# Theming and branding

FrontDir has two layers of theming:

- **Users** choose a mode (match system, light, dark, high contrast) and an accent color under
  *Settings → Appearance*. The choice is stored in that browser only (`localStorage`) and never
  sent to the server.
- **Operators and administrators** can rename the instance, add a logo, adjust the light and dark
  palettes, add accent colors and choose the default accent: in the server's configuration (below)
  or under *Admin → Branding* in the web app, where the theme is edited as the same JSON and the
  logo uploaded. A value in the configuration wins and is locked in the web app.

"Match system" follows the operating system's light/dark setting, and switches to high contrast
when the OS asks for more contrast (`prefers-contrast: more`).

## Operator settings

| Variable | Purpose |
|---|---|
| `FRONTDIR_BRAND_NAME` | Display name in the header, page title and sign-in page (1-40 characters) |
| `FRONTDIR_BRAND_LOGO_FILE` | PNG or JPEG, at most 512 KiB and 1 megapixel; shown at 28 px high |
| `FRONTDIR_THEME_FILE` | JSON theme file (below), at most 64 KiB |

### Theme file

Every key is optional. Colors are hex only (`#rgb` or `#rrggbb`).

```json
{
  "name": "Acme Files",
  "defaultAccent": "acme",
  "light": { "bg": "#fafafa", "panel": "#ffffff", "line": "#dddde3" },
  "dark":  { "bg": "#101014" },
  "accents": {
    "acme": {
      "label": "Acme red",
      "light": { "accent": "#b3261e", "accentText": "#ffffff" },
      "dark":  { "accent": "#ff8a80", "accentText": "#1a1a1a" }
    }
  }
}
```

| Token | Used for |
|---|---|
| `bg` | Page background, inputs |
| `panel` | Cards, header, dialogs, buttons |
| `text` | Body text |
| `muted` | Secondary text, labels, sizes and dates |
| `line` | Borders and dividers |
| `danger` | Destructive actions and errors |
| `rowHover` | Highlighted table rows |
| `accent` / `accentText` | Links and focus rings / text on primary buttons (per accent only) |

Accent IDs are lowercase letters, digits and hyphens (`^[a-z][a-z0-9-]{0,23}$`). Defining an ID
that already exists (`blue`, `green`, `purple`, `orange`, `teal`, `rose`) replaces that built-in.
`name` is overridden by `FRONTDIR_BRAND_NAME` when both are set.

### Validation

The theme is checked at startup, and before any web change is saved. If anything is wrong,
FrontDir **refuses to start** (or to save) and lists every problem. It never falls back silently. Besides syntax, every combination of mode and accent must
meet WCAG 2.x AA contrast (4.5:1) for each pair below:

- `text` on `bg`, `panel` and `rowHover`
- `muted`, `danger` and `accent` on `bg`, `panel` and `rowHover`
- `accentText` on `accent`

High-contrast mode is built in. It meets AAA (7:1) and cannot be changed by a theme, so an
accessible mode always exists, whatever the theme.

A failing check reads like this:

```
theme:
light mode, accent acme: muted on panel has contrast 3.21:1, needs at least 4.5:1
```

## Why it is built this way (security)

A theme sounds cosmetic, but it is content that every user's browser renders on the page where
they type their encryption passphrase. Styling can be an attack channel: CSS can fetch URLs (and
so leak data through attribute selectors), hide warnings, or overlay fake UI. Logos can be
polyglots, valid images that are also HTML or script. So theming follows the same rules as
the rest of FrontDir.

1. **Data, not code.** A theme is a list of allowlisted color tokens, never CSS. Values must match
   a strict hex grammar, so `url(...)`, `@import`, `;}` and every other piece of CSS syntax are
   rejected before they could reach a stylesheet. `/theme.css` is generated by `internal/theme`
   from those validated values, with fixed selectors.
2. **The CSP is unchanged.** Styles and scripts still come only from the server's own origin, with
   no `'unsafe-inline'` and Trusted Types enforced. Theming added no exceptions. The early
   `theme-init.js`, which applies the saved mode before the first paint to avoid a flash of the
   wrong theme, is a normal same-origin file.
3. **Readability is an integrity property.** The contrast checks also prevent a theme from making
   security text effectively invisible, such as fingerprints, "Delete forever" or sign-in errors.
4. **Fail closed.** A theme that does not pass stops startup. It is never partly applied.
5. **Images are re-encoded.** Logos are decoded and written out again as a fresh PNG. Metadata,
   appended payloads and polyglot tricks are dropped, because only pixels survive. SVG is refused
   because it is a document format that can carry script. The image's dimensions are checked from
   its header before it is decoded, so a small file declaring an enormous image (a "decompression
   bomb") is rejected without allocating memory. The logo is served as `image/png` with `nosniff`
   and a `sandbox` CSP.
6. **User preferences stay local and inert.** The browser stores only `{mode, accent}`. Both the
   early script and the app accept a value only if it is in the allowlist. Anything else in
   storage is ignored. The values are only ever matched by CSS attribute selectors and are never
   inserted as markup or CSS. The brand name is set with `textContent`.
7. **Web editing is guarded, and can be locked.** Administrators can change the name, theme and
   logo under Admin → Branding. That puts branding within reach of a stolen administrator session,
   so the guards are layered. Every rule above still applies, because the web and the configuration
   go through the same validator: a web theme is still only colors, contrast-checked, and a logo is
   still re-encoded pixels. Saving needs a recent re-authentication at the identity provider, not
   just a session (ADMIN_GUIDE §7, "Confirm it's you"). Every change is audited as
   `settings.changed`. Setting `FRONTDIR_BRAND_NAME`, `FRONTDIR_THEME_FILE` or
   `FRONTDIR_BRAND_LOGO_FILE` locks that item to the configuration, and `FRONTDIR_WEB_SETTINGS=false`
   locks everything. So even a theme saved by an attacker cannot inject markup or script, hide a
   warning or break contrast: the most it can change is colors, the name and the logo, which the
   re-authentication and the audit trail make hard to do unnoticed.
